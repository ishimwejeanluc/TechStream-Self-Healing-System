# TechStream self-healing observability lab

Monitors a web app on the four Golden Signals, detects a rising error rate on its
own, and restarts the failing service before an engineer is involved. Finishes
with a correlation report that names the likely trigger.

Verified end to end: the loop closed itself in **2.7 seconds** from alert to
restart, with the app independently confirming its own restart. Real timestamps
are in [docs/RUNBOOK.md](docs/RUNBOOK.md).

> Traffic in this lab is generated by `chaos/chaos.sh`. These are simulated
> requests. No real users are involved anywhere in this repo.

## Quick start, locally

```bash
cp .env.example .env
# set GF_SECURITY_ADMIN_PASSWORD and REMEDIATION_WEBHOOK_TOKEN
#   openssl rand -base64 24
#   openssl rand -hex 32

make up               # build and start, waits until ready
make remediator-up    # local remediation stand-in, points Alertmanager at it
make chaos-errors     # inject the incident and watch it heal
make rca              # correlate what happened
```

Then open http://localhost:3000/d/techstream-golden-signals.

`make loop` runs the whole sequence including a 5 minute idle gap first, so the
RCA gets a clean baseline.

## Deploying to AWS

Terraform is applied. `bootstrap` created 7 resources (the S3 state backend) and
`stack` created 17 (EC2, security group, IAM, SSM document, Lambda, Function URL,
log group). `infra/grafana-ml` created the ML jobs.

The instance is a running `t3.medium`, roughly $0.05 per hour. Run
`make tf-destroy` when finished, or it bills until you do.

### One time: the state backend

The main config keeps state in S3, but that bucket has to be created by Terraform
too. `infra/bootstrap` breaks the cycle by using local state and creating only the
backend.

```bash
cd infra/bootstrap
cp terraform.tfvars.example terraform.tfvars
terraform init
terraform apply
terraform output backend_block     # already matches infra/stack/versions.tf
```

The bucket has versioning, encryption, all public access blocked, a TLS-only
policy, and a lifecycle rule keeping noncurrent versions. Locking is S3 native
(`use_lockfile`), so no DynamoDB table. A table is available behind
`create_dynamodb_lock_table` for Terraform older than 1.10.

### Then: the stack

```bash
cd infra/stack
cp terraform.tfvars.example terraform.tfvars
# set allowed_cidr to your IP as a /32:  curl -s https://checkip.amazonaws.com
# set remediation_webhook_token:         openssl rand -hex 32

terraform init        # initialises the S3 backend from bootstrap
terraform plan
terraform apply
terraform output
```

If the bucket name or region differs from the literals in
`infra/stack/versions.tf`, pass them at init time instead of editing:

```bash
terraform init -reconfigure \
  -backend-config="bucket=$(terraform -chdir=../bootstrap output -raw state_bucket_name)" \
  -backend-config="region=eu-west-1"
```

Use `-reconfigure` for a fresh setup, `-migrate-state` only when moving existing
local state into the bucket.

### Then: the app on the instance

```bash
IP=$(terraform -chdir=infra/stack output -raw instance_public_ip)
rsync -av --exclude '.git' --exclude '.terraform' ./ ubuntu@$IP:/opt/techstream/

ssh ubuntu@$IP
cd /opt/techstream
cp .env.example .env      # set the password and token
make up

TOKEN=$(grep '^REMEDIATION_WEBHOOK_TOKEN=' .env | cut -d= -f2)
make configure URL="<lambda_function_url>?token=$TOKEN"
```

`docker-compose.yml` must end up at `/opt/techstream`, because the SSM document
runs `cd /opt/techstream && docker compose restart app`.

Do **not** run `make remediator-up` on the instance. It mounts the Docker socket,
which is root equivalent. On EC2 the Lambda plus scoped IAM does the same job.

## How the pieces fit

| Component | Role |
|---|---|
| Flask app | Serves traffic, exposes metrics, injects faults on demand |
| Prometheus | Scrapes app, node-exporter and cAdvisor. Evaluates the alert rules |
| Alertmanager | Routes `HighErrorRate` to remediation, everything else to a null receiver |
| Lambda plus SSM | Restarts the app container, least privilege, deployed path |
| Grafana | Provisioned Golden Signals dashboard, 5 rows, 12 panels |
| chaos.sh | Injects the incident, records the window |
| rca.py | Correlates the window, names the trigger |

The error ratio expression is identical in the dashboard and the alert rule, so
the line you watch and the line that restarts the app cannot disagree:

```promql
100 * sum(rate(http_requests_total{status=~"5.."}[1m]))
  / clamp_min(sum(rate(http_requests_total[1m])), 1)
```

## Alert rules

| Alert | For | Remediation | Why |
|---|---|---|---|
| `HighErrorRate` | 1m | restart | The only one wired to automation |
| `AppDown` | 2m | none | A dead app produces no error ratio at all |
| `HighLatencyP95` | 2m | none | A restart does not fix a slow host |
| `HostCpuSaturation` | 2m | none | Scaling out is the answer, not a restart |

Routing is fail closed: the default receiver is the null receiver, so a new alert
cannot inherit remediation by accident. Verify with `make routes`.

## Grafana Cloud Machine Learning

The AI/ML root cause artifact. Chosen over Amazon DevOps Guru because DevOps Guru
reads CloudWatch, and this lab's application errors live in Prometheus. For the
incident this lab remediates, host CPU peaked at 15.8 percent while 771 requests
failed, so DevOps Guru would have reported nothing.

Prometheus ships a copy of its metrics with `remote_write`. Local scraping and
local alerting are unaffected: if Grafana Cloud is unreachable, the self-healing
loop keeps working.

An allowlist ships **121 series out of about 3600**, because the rest is
node-exporter, Prometheus and Alertmanager internals that no panel, rule or ML job
queries. It also filters cAdvisor down to this project's containers, since cAdvisor
reports every container on the host.

```bash
make cloud-token TOKEN=glc_...   # Cloud Portal token, scope metrics:write
make cloud-status                # 0 failures, Active Series climbing
make ml-apply                    # forecast job, DBSCAN detector, insight alerts
make ml-baseline                 # 10 min healthy traffic BEFORE any chaos
```

Two separate tokens are involved and they are not interchangeable: a `glc_` Cloud
Portal token for `remote_write`, and a `glsa_` Grafana service account token for
Terraform. Full detail in [docs/grafana-ml-setup.md](docs/grafana-ml-setup.md).

The ML alerts carry `remediation = "none"` and are routed nowhere. The Prometheus
`HighErrorRate` rule remains the only thing that triggers a restart, so a
mistrained model cannot restart the app.

**Models need a training window.** If chaos runs while a model is still learning,
it learns that a 40 percent error rate is normal and will never flag it.

## Secrets

Nothing secret is committed.

| Secret | Lives in | Gitignored |
|---|---|---|
| Grafana admin password | `.env` | yes |
| Remediation shared token | `.env` and `infra/stack/terraform.tfvars` | yes |
| Webhook URL including token | `monitoring/alertmanager/webhook_url` | yes |

Alertmanager reads the webhook URL at notify time via `url_file`, so the token
never enters a committed config. The stack starts fine before it is configured.

Grafana refuses to start without an explicit password rather than defaulting to
`admin/admin` on a public port.

`.terraform.lock.hcl` **is** committed, deliberately, so every machine resolves
the same provider build (aws 6.60.0).

## Security notes

- `allowed_cidr` controls who reaches ports 22, 3000, 8080, 9090 and 9093.
  Prometheus (9090) and Alertmanager (9093) have **no authentication at all**,
  and anyone reaching 9093 can post an alert that triggers a restart. A `/32` of
  your own IP is the safe setting. `0.0.0.0/0` is permitted for lab convenience,
  since a changing home IP otherwise locks you out, but it exposes both of those
  services to the internet. The earlier validation rule that refused
  `0.0.0.0/0` was removed deliberately to allow this.
- The Lambda Function URL is `authorization_type = "NONE"`, because Alertmanager
  cannot sign SigV4. The `?token=` shared secret is the **only** gate on
  remediation. Treat it like a password.
- `ssm:SendCommand` is scoped to one custom document and one instance ARN.
  Granting it on `AWS-RunShellScript` would be arbitrary root on the box.
- IMDSv2 is required on the instance, closing the SSRF path to credentials.
- Egress is open, an accepted exception recorded in
  `infra/modules/network/main.tf` with what a proper fix would need.
- The local remediator mounts the Docker socket and is profile gated for that
  reason. Never on EC2.

## Teardown

```bash
make down          # local stack and volumes
make ml-destroy    # Grafana Cloud ML jobs, independent of AWS
make tf-destroy    # AWS main stack: EC2, Lambda, SG, IAM
```

Then delete the `terraform-techstream-ml` service account in Grafana, which
revokes its token, and revoke the `glc_` token in the Cloud Portal.

`infra/bootstrap` is destroyed **last**, because it holds the bucket containing
the main stack's state. The bucket also carries `prevent_destroy = true`, so
removing it means deleting that lifecycle block first. Full commands, including
emptying a versioned bucket, are in the runbook.
